# 接口审查清单

审查目标：找出**会在生产环境出问题**的缺陷，而不是风格偏好。

## 使用方式

1. 按五个维度**逐项**检查，不跳项、不抽样。每项即使通过也要在心里过一遍。
2. 每个发现必须给出：位置（类 + 方法 + 行号）→ 严重级别 → 成因 → 修改建议（带代码片段）。
3. 拿不准的地方标注「需确认」，并说明需要什么信息才能判断，不要编造结论。
4. **只输出清单，不修改代码。** 用户确认后再改。
5. 信息不足时（看不到表结构、看不到上游调用方），先说明审查范围与盲区。

审查范围默认包含：Controller、Service、ServiceImpl、Mapper、DTO/VO、涉及的配置。

---

## 一、正确性

- [ ] **字段对齐**：DTO/VO 字段名、类型、必填性与 API 文档、数据库表结构一致
- [ ] **响应结构**：返回值符合统一响应体约定，没有裸对象/裸 `Map`
- [ ] **错误码**：使用错误码枚举，未硬编码数字，未复用已有码值表达新语义
- [ ] **参数校验**：必填、长度、范围、格式均有校验；`@Valid` 未遗漏
- [ ] **边界值**：数量为 0/负数、字符串为空、集合为 `null` 或空、金额为 0 的场景
- [ ] **状态流转**：状态机的每个转换都有前置状态校验，非法转换被拒绝
- [ ] **金额计算**：使用 `BigDecimal`，比较用 `compareTo`；未使用 `double`
- [ ] **时间处理**：使用 `LocalDateTime`，时区一致
- [ ] **分页**：有总量、有上限、排序字段明确（避免分页乱序导致数据重复或遗漏）

## 二、并发与一致性

- [ ] **库存/余额扣减**：存在并发扣减时，是否用原子 SQL（`where stock >= num`）或加锁保护
- [ ] **超卖检查**：扣减后是否允许负库存，是否在 SQL 层兜底而非仅应用层判断
- [ ] **幂等性**：重复请求（网络重试、用户连点、MQ 重投）是否会产生重复数据或重复副作用
- [ ] **唯一约束**：幂等是否依赖数据库唯一索引兜底，而非仅靠先查后插
- [ ] **锁的使用**：加锁粒度是否合理、是否设置超时、释放是否在 `finally`
- [ ] **锁内校验**：加锁后是否重新校验业务状态（防「检查后使用」竞态）
- [ ] **事务边界**：
  - `@Transactional` 是否标在 `public` 方法且由外部调用（避免自调用失效）
  - 是否显式声明 `rollbackFor = Exception.class`
  - 事务内是否包含远程调用、MQ 发送、文件上传等外部 IO
  - 是否存在大事务（事务内循环、批量写、长耗时操作）
- [ ] **分布式事务**：跨服务写操作是否有一致性保障，回滚失败是否有补偿

## 三、健壮性

- [ ] **远程调用**：是否设置超时、是否处理调用失败、是否有降级
- [ ] **MQ 消费者**：是否幂等、是否手动 ACK、异常时是否会导致消息丢失或无限重试
- [ ] **消息可靠投递**：关键消息是否有本地消息表或等价保障，是否依赖「发送一定成功」的假设
- [ ] **空值与异常**：`Optional`/`null` 处理完整，未出现 `NullPointerException` 风险点
- [ ] **资源释放**：流、连接、锁在异常路径下也能释放
- [ ] **降级返回**：限流/熔断触发时返回用户友好提示，而非堆栈或英文错误
- [ ] **日志**：关键分支有日志；异常打印完整堆栈（`log.error("...", e)`）而非只打 message
- [ ] **敏感信息**：日志中未打印密码、Token、身份证、完整手机号

## 四、安全

- [ ] **鉴权**：接口是否需要登录，是否遗漏鉴权注解或白名单配置
- [ ] **越权（水平）**：操作资源前校验归属（如「订单是否属于当前用户」），不只信任传入的 ID
- [ ] **越权（垂直）**：管理端接口有角色校验，普通用户无法调用
- [ ] **服务端重算**：金额、折扣、积分等关键数据由服务端计算，不信任前端传入
- [ ] **SQL 注入**：动态 SQL 使用参数绑定，未拼接用户输入
- [ ] **敏感字段**：VO 未返回密码、内部状态、成本价等不该暴露的字段
- [ ] **内部接口隔离**：内部/回调接口不经网关暴露，并校验调用凭证
- [ ] **回调验签**：第三方回调（支付等）验证签名，未验签直接信任请求体
- [ ] **批量操作**：批量接口有数量上限，防止一次请求拖垮服务
- [ ] **XSS/富文本**：用户输入的内容在输出时被转义或过滤

## 五、可维护性

- [ ] **分层职责**：Controller 无业务逻辑，Service 无 HTTP 细节，Mapper 无业务判断
- [ ] **重复代码**：同一逻辑出现三次以上，是否应抽取
- [ ] **幽灵代码**：是否存在无引用的类、方法、字段、常量
- [ ] **过度抽象**：是否为只有单一实现的逻辑引入了不必要的接口或工厂
- [ ] **命名**：类名/方法名/变量名表达意图，未出现 `data`、`list1`、`temp` 这类无意义命名
- [ ] **魔法值**：常量、状态码、阈值是否提取为常量或枚举
- [ ] **注释**：无复述代码的无效注释；复杂逻辑有「为什么」的说明
- [ ] **API 文档注解**：新增接口有 `@Tag` / `@Operation`，参数说明完整
- [ ] **依赖**：未新增未经验证的 Maven 依赖
- [ ] **N+1 查询**：未在循环中查询数据库

---

## 严重级别定义

| 级别 | 判定标准 | 处理要求 |
|---|---|---|
| **P0 阻断** | 会导致数据错误、资金损失、越权访问、生产故障 | 必须修复后才能合入 |
| **P1 严重** | 特定条件下会出错（并发、重试、异常路径），或存在明显安全隐患 | 本次迭代内修复 |
| **P2 一般** | 不影响正确性，但违反项目规范、埋下维护隐患 | 建议修复，可排期 |
| **P3 建议** | 风格与可读性优化 | 可选 |

判定原则：**能说清「什么条件下会出什么错」的才是 P0/P1**，说不清的降级为 P2/P3。

## 输出模板

```
## 审查结论
<一句话总体判断：可以合入 / 需修复后合入 / 存在阻塞问题>

## 问题清单

### [P0] <问题标题>
- 位置：XxxServiceImpl.java:42 `deductStock`
- 现象：<什么条件下会发生什么>
- 成因：<为什么会写错>
- 建议：<怎么改，附代码>

### [P1] <问题标题>
...

## 未发现问题项
<简述已检查且通过的部分，让使用者知道覆盖范围>

## 审查盲区
<看不到的信息，以及需要提供什么才能继续>
```

**排序规则**：按严重级别从高到低排列，同级按代码执行顺序。

**数量控制**：P0/P1 必须全部列出；P2/P3 只列最有价值的若干条，不堆砌。

## 必查项（写代码时自查用）

写完后至少过一遍这 8 条，发现问题在交付说明中主动列出：

1. 字段名与文档、表结构是否一致
2. 入参校验是否完整
3. 是否有越权风险（资源归属校验）
4. 并发场景是否有原子操作或锁保护
5. 事务边界是否正确（位置、范围、rollbackFor）
6. 重复请求是否幂等
7. 异常是否被正确抛出与处理，日志是否完整
8. 是否有未使用代码或被误导出的新增依赖
